## 2026-11-19 — Un fichier `.env` pour choisir l'API Spring en local

**Demande** : le bouton « Continuer avec Discord » n'apparaissait pas en local. Après le diagnostic, l'utilisateur a voulu que le front local s'appuie sur l'API de production, puis qu'un `.env` porte cette adresse « pour l'utiliser partout ».

**Diagnostic de l'agent** : le bouton dépend de `GET /api/auth/providers`. Le Spring local (conteneur démarré le 2026-11-16) date d'avant la connexion Discord : il répond `401` sur cette route. Son `.env` n'a pas non plus de `DISCORD_CLIENT_ID`. Le front n'était pas en cause.

**Questions de l'utilisateur en chemin** : qu'est-ce que nginx, et peut-on simplifier la chaîne de production (passer outre nginx, déplacer Spring, ou déplacer ce front dans l'ancien projet) ? L'agent a déconseillé les deux premières pistes : la première ouvrirait le réseau privé de l'ancien projet, base comprise, et la seconde casserait l'ancien site et le mod. La troisième est la bonne cible, mais **après la correction** : le dépôt et le site sont encore évalués, on ne touche pas à la production d'ici là. L'agent avait d'abord justifié ce report par l'oral, qui était déjà passé ; l'utilisateur l'a corrigé.

**Mesure avant de coder** : un serveur de dev lancé avec `NITRO_API_URL=https://celeste.matthisripoche.com` affiche bien le bouton (`{"discord":true}`). Mais la `redirect_uri` renvoyée par Spring est celle de l'**ancien site** : Traefik réécrit `X-Forwarded-Host` sur l'adresse publique, comme mesuré en production pour #35. En local contre la production, la connexion Discord ne peut donc pas aboutir. L'utilisateur en a été prévenu, ainsi que du fait que les écritures touchent les vraies données.

**Réalisation** :
- `.env.example` versionné (`.gitignore` : `!.env.example`), `.env` ignoré.
- `npm run dev` : Vite ne lit `.env` que pour `import.meta.env`, côté client. Le serveur Nitro de dev, lui, lit `process.env`, et la mesure l'a confirmé : sans code, la requête partait encore vers le Spring local. `chargerEnvLocal` (`vite.config.ts`) recopie `NITRO_API_URL` dans `process.env`, seulement en `serve` hors tests, sans écraser une variable du shell.
- `npm run preview` : `node --env-file-if-exists=.env` (Node 24).
- L'image Docker ne contient pas `.env` (`deploy/Dockerfile.dockerignore` l'exclut déjà) : la production garde l'adresse du compose.

**Vérifications** : dev avec `.env` → API de production ; variable du shell prioritaire → API locale ; sans `.env` → API locale ; preview avec `.env` → API de production ; 450 tests et build OK.

**Erreur de l'agent rattrapée** : au premier essai, la variable du shell semblait ignorée. L'agent avait arrêté `npx` et non le processus Vite qu'il lance : le premier serveur d'essai, resté en vie sur le port, répondait au second test. Relancé avec le binaire `vite` directement, le comportement attendu est apparu.
